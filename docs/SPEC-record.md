# Запись сессии, хранение и выгрузка

## Версия формата
`cb-record-2` — с кодом причины (задача З-1, решение Р-8). Предыдущая — `cb-record-1`.
Старые записи при чтении получают `reasonCode` по строке; неизвестная строка — `R00` и `reasonUnknown: true`.
Менять только с записью в `DECISIONS.md`.

## Состав записи
| Группа | Поля | Происхождение |
|---|---|---|
| служебное | id, fmt, startedAt, tz, durationSec | — |
| ключ | reason, reasonCode, reasonGroup — в корне записи | выбрано человеком |
| stated | pre{ctx, area, areaOther, quality, level}, post{level, change, done, hinder}, note, postSkipped | заявлено человеком |
| set | organ, params{t-in, t-h1, t-out, t-h2, s-h2, c-freq, c-force, heart-rate}, preset, reactMethod (`voice` / `slider`, фактический способ; с З-12, Р-13) | задано настройкой |
| measured | device, samples; ряды `rr` и `spo2` — только в `series` (З-2, З-3) | измерено прибором |
| marked | пусто; события этапов и ряд реакции — в `series.events` и `series.react` (З-2, Р-12) | отмечено во время сессии |
| derived | holds, holdSec[] (с), holdOpen[], lastHoldOpen, contactSec[] (с, `null` без контакта), boundaryReached, response (±1 / `null`) — из `series.events` при сохранении (З-11); позже ВСР (З-3), acc* (З-8) | вычислено моделью |

`holdOpen` — задержка закончилась без `release` (следующим `hold` или концом сессии); её `holdSec` — нижняя граница. Записи без `derived` получают его при чтении из `series`, пока сырьё есть; сама запись не переписывается.

Причина — ключ записи, а не ответ: она задаёт шаблон и набор вопросов, по ней строятся указатель и сводка. Поэтому лежит в корне, рядом со служебными полями. `areaOther` — свободный текст, если область выбрана как «другое».

Состояния ответа: **дан**, **пропущен** (`__skipped`), **не задавался** (поля нет).

## Хранилище (IndexedDB `cb_records`)
- `index` — строка на сессию для списков и сводок (~200 байт), с `reasonCode`; поля: id, at, reason, reasonCode, area, areaOther, pre, post, dur, device.
  `pre`, `post` — ответ на главный вопрос (`level`, 0–10) или `null`, если ответа нет: пропущен или не задавался. Различие «пропущен / не задавался» хранится только в `sessions.stated`. В строках, записанных до 2026-10-02, в `post` может стоять `'__skipped'` — читается как пропуск, строка не переписывается.
  Производные для сводки (Р-14): `change` — ответ «что изменилось» или `null`; `holdN`, `holdSum` — число и сумма (с) полных задержек; `holdOpenN` — оборванные задержки; `contact` — был ли контакт.
  Источник истины — `sessions` и `series`; `index` их дублирует ради скорости, при расхождении верна `sessions`. В строках до Р-14 полей нет — сводка дочитывает их из `sessions`, строка не переписывается.
- `sessions` — полная запись без сырья (<1 КБ).
- `series` — сырые ряды (~10 КБ на 15 минут), запись на сессию, ключ равен id сессии (З-2):
  - `fmt` — версия формата;
  - `events` — `[{t, e, v?}]`, `t` в секундах от старта (0,1 с). `e`: `start`, `hold` (начало задержки), `contact` (А → Б1), `b2` (Б1 → Б2), `release`, `response` (`v` = ±1), `end`;
  - `react` — ряд реакции процесса «▶ Запустить процесс», если он шёл во время сессии: одно значение в секунду (последнее в секунде), `null` в секундах без точек; иначе `[]`;
  - `rr`, `spo2` — только при подключённом датчике (З-3), без датчика полей нет.

  Сырьё не перезаписывается и не пересчитывается. `sessions`, `index` и `series` пишутся одной транзакцией.

## Сводка (З-4, выполнено 2026-10-02)
📊 Аналитика, вкладка «Сводка» (первая); нынешняя аналитика — вкладка «Подробно».
Период по умолчанию 90 дней, переключение на 30 и на всё время.
Строка на пару «причина + область»: число сессий, среднее до, среднее после,
разница после − до (помогает ли в моменте), тенденция значения до (меняется ли фон) — наклон прямой, баллов за 30 дней.
Порог: при менее чем 5 сессиях средние не показывать.
Наверх выносятся три сигнала: рост значения до (у `well` — снижение), появление отметок «усилилась», обрыв практики. Пороги — в Р-14, предварительные.
Одна строка по периоду: средняя длительность полной задержки (оборванные — отдельным счётчиком) и доля сессий с контактом среди сессий с задержками.
Ниже: регулярность (доля дней с сессиями, самый длинный перерыв до сегодня), доля пропусков главного вопроса до и после, последние 5 заметок дословно.
Источник — `index` (Р-10, Р-14); заметки — из `sessions`, `series` не читается. При пустом журнале — пример на вымышленных данных, в базу не пишется.

## Выгрузка (З-5, выполнено 2026-10-07)
Под сводкой, вкладка «Сводка». Выгружается то, что показано: текущий период сводки, те же данные; период — в файле и в имени файла.
В примере на вымышленных данных и при пустом периоде выгрузки нет.

| Получатель | Как | Имя файла |
|---|---|---|
| врач | окно печати браузера (PDF сохраняет сам) или отдельной кнопкой файл HTML | `svodka-90d-ГГГГ-ММ-ДД.html` |
| ИИ-ассистент врача | JSON со словарём полей | `svodka-vrach-ii-90d-ГГГГ-ММ-ДД.json` |
| ИИ пациента | то же плюс `pairs` | `svodka-pacient-ii-90d-ГГГГ-ММ-ДД.json` |
| журнал | отдельная кнопка и согласие; сырьё — флажок, по умолчанию выключен | `zhurnal-ГГГГ-ММ-ДД.json` |

Период в имени: `30d`, `90d`, `vse`. Формат выгрузки — `cb-export-1` (Р-15).

**Обязательная строка** в каждом файле: версия формата, дата и «Материал анамнеза, а не диагностические данные: часть показателей заявлена пациентом.»

**Страница для врача.** Шапка независимо от периода: «Практика с … · всего сессий: N» (`summarize().since`, `total` — по всему журналу), затем период сводки. Сигналы, задержки, строки по причине и области (порог 5 сессий, как в сводке), регулярность и пропуски, последние 5 заметок дословно.
Помечена «Черновик», пока не выполнена З-10 (константа `DOCTOR_DRAFT`). Машинные форматы от этого не зависят.

**JSON.** Поля, их происхождение, единицы и способ расчёта описаны в одной таблице в коде (`SPEC` слоя выгрузки, собрана из `COMMON`, `SIG`, `LINE`, `LINE_AVG`, `PAIRS`): данные и словарь `dictionary` строятся обходом этой таблицы, поэтому не расходятся. Ключ словаря — путь поля (`lines[].diff`), значение — `origin`, `unit`, `method`. Метки происхождения — из таблицы «Состав записи»: выбрано человеком, заявлено человеком, вычислено моделью, служебное.
`pairs` (ИИ пациента) — факты, без вывода: по каждой паре «причина + область» за период число сессий, число сессий с обоими ответами, средняя разница после − до, `few` при менее чем 5 сессиях, первая и последняя дата.

**Журнал.** Все сессии за всё время (`sessions`, с производными), без сырья; с флажком — плюс `series`. В строке согласия — примерный размер файла: ~1,2 КБ на запись, сырьё ~10 КБ на 15 минут, с датчиком втрое больше. В файле — `origins`: происхождение групп записи.

**Согласие.** Перед каждой выгрузкой — свёрнутая строка «период · состав · получатель»; по нажатию разворачивается полный состав. «Выгрузить» или «Отмена»; до подтверждения ничего не формируется.

## Архив и импорт (З-6, выполнено 2026-10-07)
📊 Аналитика → «Сводка», блок «Архив» под выгрузкой. Архив — не выгрузка: он возвращает данные владельцу, поэтому в нём нет словаря, меток происхождения и оговорки про анамнез. Нужны полнота и точность.

**Файл** `arhiv-ГГГГ-ММ-ДД.json`, формат `cb-archive-1` (Р-16):
- `format`, `createdAt`, `dbVersion` (версия базы `cb_records`);
- `records` — `counts` по хранилищам, `crc`, `stores: {index, sessions, series}`; записи как лежат в базе (`DB.raw`), без достройки при чтении — без подставленного `reasonCode` и посчитанного `derived`;
- `settings` — отдельная часть со своей `crc`: `keys` — строки `localStorage` как есть (`cb_settings_v1`, `cb_hints_off`, `organTargets`; `null` — ключа не было);
- `legacy` — старые журналы в `localStorage`, тоже строками как есть, своя `crc`: `sessionLog_v1`, `latencyLog_v1`, `fbSessions_v1` (Р-17). Часть необязательная: архивы без неё импортируются.

Контрольная сумма — CRC-32 по `JSON.stringify` части: ловит повреждение файла и работает без защищённого адреса. Не защита от подделки.
Ограничение: архив — JSON, поэтому в записях допустимы только JSON-значения (без `undefined`, `NaN`, дат-объектов). Круговой тест это проверяет.

**Импорт.** Перед записью — разбор: сколько добавится, совпадёт и различается. По id сессии сравниваются все три хранилища без учёта порядка ключей:
- id нет в базе — добавляется;
- совпадает во всех хранилищах — пропускается;
- различается — сохраняются обе: копия получает id `<id>~impN` во всех трёх хранилищах, в `index` и `sessions` — поле `importedConflict: {of, at}`. Если такая копия уже есть, повторный импорт её не дублирует.

Записи пишутся одной транзакцией (`DB.putMany`). Испорченная сумма записей — импорт отказывает, база не тронута; испорченная часть настроек — записи импортируются, настройки нет.
Настройки восстанавливаются только по отдельному флажку (по умолчанию выключен) и применяются после перезагрузки страницы.

**Дата последнего архива** — `localStorage` `cb_archive_v1` (`{lastAt}`), в архив не входит. Если она потеряется, З-7 считает, что архива не было, и сырьё не сворачивает.

**Напоминание** — в блоке «Архив» и строкой на экране после сессии (`#ps-archive`): больше месяца с последнего архива (или с первой сессии, если архива не было); пока архива не было — ещё на каждой десятой сессии.

**Старые журналы** восстанавливаются вместе с записями, без отдельного согласия: это данные владельца. Журнала на устройстве нет — записывается строка из архива как есть. Есть — объединение по элементам с учётом повторов: одинаковые не дублируются, новые дописываются в конец, свои элементы устройства остаются. Журнал на устройстве, который не читается как массив, не трогается; повреждённая часть `legacy` — журналы не восстанавливаются, записи импортируются. Перед импортом показано, сколько элементов добавится.

*Известное поведение.* При объединении архивные элементы встают после элементов устройства, по времени журнал не сортируется (метка `ts` есть не во всех журналах). Модель показывает хвост журнала (последние 5 записей, последние 8 кривых), поэтому там могут оказаться архивные элементы, даже если они старше. На устройстве без своих журналов порядок сохраняется точно. Оставлено как есть по решению владельца: случай редкий.
